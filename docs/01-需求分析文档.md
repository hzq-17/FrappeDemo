## 1. 文档目的与范围

### 1.1 目的

本文档用于回答三个问题：

1. **要做什么** —— 把"一份用户服务开通/流失单据、一份增长报表、一个大屏页面"的原始诉求，拆解为可开发、可验收的功能需求条目。
2. **做到什么程度算完成** —— 给出可量化的验收标准（功能、性能、交互、权限）。
3. **边界在哪里** —— 明确本期不做的事，避免范围蔓延。

本文档是《可行性分析文档》与《详细设计文档》的唯一需求输入源。设计文档中的每个设计点都应能回溯到本文档的 FR/NFR 编号（追踪矩阵见《详细设计文档》附录）。

### 1.2 本期范围（In Scope）

| 编号 | 范围项 | 说明 |
| --- | --- | --- |
| S1 | 可运行的 Frappe 环境 | 本地/演示环境可启动，并已开启开发者模式（Debug） |
| S2 | 自定义 App | 通过 `bench new-app` 创建，命名 `user_growth`，含独立模块与目录结构 |
| S3 | 单据（Doctype） | 用户服务开通 / 流失信息单据，含完整字段、校验、权限，并预置 mock 数据 |
| S4 | 报表（Report） | 用户增长与流失分析报表，基于 S3 数据，支持筛选、分组、图表与导出 |
| S5 | 页面（Page） | 用户增长数据大屏，基于 S3 数据，适配大屏展示，支持自动刷新 |
| S6 | 交付配套 | 启动/生成数据/演示脚本、必要文档，保证"新机器上 30 分钟内可复现" |

### 1.3 本期不做（Out of Scope）

- 接入真实业务数据库、CRM、计费系统或埋点系统（本期数据全部为合成 mock 数据）。
- 用户体系改造：注册、登录、SSO、企业微信/钉钉集成。
- 预测类算法（流失预测模型、LTV 预测模型）——仅做描述性统计与规则型预警清单。
- 移动端原生 App / 小程序；大屏为 Web 展示，不做触控 Kiosk 定制。
- 多币种、多时区、多租户（`site` 级多租户）支持。
- 生产级高可用架构（负载均衡、读写分离、集群部署）。

### 1.4 读者对象

产品/业务评审人、技术评审人、开发实施人、测试人员。文档中"用户"一词在没有特别说明时指**被测系统的使用者**（业务人员），而非被统计的"用户服务记录"中的终端客户。

## 2. 项目背景与业务目标

### 2.1 背景

订阅制（SaaS）业务的经营健康度由一条主线决定：**开通（新增）→ 留存（续费）→ 流失（Churn）**。这条主线上的数据通常散落在计费系统、CRM、工单系统与人工 Excel 中，导致三个典型问题：

- 口径不统一：市场部说"本月新增 1200 用户"，财务部按付费口径只有 480，客户成功部按生效口径是 512。
- 看不见流失：缺少统一的流失原因与流失金额视角，只能事后"补锅"。
- 汇报成本高：每次经营会前需要 2~3 人日人工汇总、拼图、做 PPT。

本项目在 Frappe 框架上搭建一套**从数据录入到分析展示的完整闭环**：以一张"用户服务记录"单据承载原始事实，以一份报表承载分析能力，以一个全屏大屏承载汇报与监控场景。

### 2.2 业务目标

目标是让决策者在 **5 分钟内**回答以下四个问题：

| 问题 | 承载交付物 |
| --- | --- |
| 我们现在还有多少在服用户？相比上期是涨还是跌？ | 大屏 KPI 区 / 报表汇总行 |
| 本期新增、流失各是多少？净增长是否健康？ | 大屏趋势图 / 报表主表 |
| 哪个渠道、哪个区域、哪个套餐贡献最好？哪里在漏水？ | 大屏分布与漏斗区 / 报表分组模式 |
| 用户为什么流失？哪些客户值得挽回？ | 单据流失字段 + 大屏流失原因分布 + 预警清单（P1） |

### 2.3 成功标准

1. 三项交付物均可在浏览器中直接打开并正常展示数据，无报错、无空面板。
2. 大屏在 1920×1080 与 3840×2160 下均无滚动条、无元素重叠、远距离（≥3 米）可读。
3. 报表在 12 个月数据、约 8,000 条记录规模下，响应时间 P95 ≤ 1.5 秒。
4. 单据的校验规则可在 100% 的非法输入场景拦截（缺失必填、日期倒置、流失无原因等）。
5. 环境搭建、mock 数据生成、页面访问三步在文档指导下可一次成功，无需人工排错。

## 4. 术语与核心指标口径

### 4.1 记录语义定义（**最关键的口径前置**）

"用户服务开通/流失信息单据"存在两种建模语义，必须先行澄清：

| 语义 | 一行代表 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A. 事件型 | 一次动作（开通 / 续费 / 升级 / 流失） | 可还原完整动作序列 | 计算"期末在服数"需要累计去重，SQL 复杂、性能差 |
| B. 生命周期型 | 一个用户的一段服务订阅（从开通到流失） | 存量/流失率/生命周期可直接计算，性能好，贴合"开通/流失单据"字面 | 续费过程需另表承载 |

**本期采用 B 为主**：一行 = 一段服务生命周期，字段同时承载"开通信息"与"流失信息"。同一终端客户流失后被唤回，会形成**第二段生命周期**（用"生命周期序号"区分），从而既保住口径简单，也不丢失"唤回"这一业务事实。续费/升级/降级等过程性动作通过可选子表（P1）承载。

### 4.2 术语表

| 术语 | 英文 | 说明 |
| --- | --- | --- |
| 在服用户 | Active Subscription | 统计截止时点仍处于有效服务期内的记录 |
| 开通 | Activation | 一段服务生命周期的开始 |
| 流失 | Churn | 一段服务生命周期的终止（付费用户停止续费或主动退订） |
| 唤回 | Win-back | 曾流失用户重新开通服务，产生新的一段生命周期 |
| 净增长 | Net Growth | 期间新增数 − 期间流失数 |
| 生命周期 | Lifecycle | 从开通日到流失日的持续天数 |
| MRR | Monthly Recurring Revenue | 月度经常性收入；本期按套餐月费口径折算 |
| 大区 | Region | 华东/华北/华南/华中/西南/西北/东北/海外 |

### 4.3 指标口径表

> 所有指标都必须能回答"分子是什么、分母是什么、时间落在哪个区间"。本节即系统的"指标字典"，报表与大屏必须共用同一口径实现。

| 指标 | 定义与公式 | 计算语义（对单据字段的依赖） | 备注 |
| --- | --- | --- | --- |
| 新增用户数 | 期间内发生的生命周期开始数 | `activation_date ∈ [start, end]` 的记录数 | 可拆分"新开通"与"唤回"（按 `lifecycle_seq = 1` 区分） |
| 流失用户数 | 期间内发生的生命周期结束数 | `churn_date ∈ [start, end]` 且状态为已流失 | 不含暂停、不含到期未处理 |
| 净增长 | 新增用户数 − 流失用户数 | 上述两项相减 | 允许为负 |
| 期初在服用户数 | 期初时点仍在服务中的记录数 | `activation_date ≤ start−1day` 且 (`churn_date` 为空 或 `> start−1day`) | 区间重叠法 |
| 期末在服用户数 | 期末时点仍在服务中的记录数 | `activation_date ≤ end` 且 (`churn_date` 为空 或 `> end`) | 北极星指标候选 |
| 平均在服用户数 | 期间日均在服数 | 逐日在服数之和 ÷ 期间天数 | 用于流失率分母的备选口径 |
| 流失率（默认口径） | 期间流失数 ÷ 期初在服数 | 上述两项相除 | 必须在报表中显式标注分母口径 |
| 流失率（备用口径） | 期间流失数 ÷ 平均在服数 | 上述两项相除 | 大屏展示时标注"平均口径" |
| 新增 MRR | 期间开通记录的月费之和 | Σ 新增记录的 `mrr` | 唤回记录计入 |
| 流失 MRR | 期间流失记录的月费之和 | Σ 流失记录的 `mrr` | 反映收入损失 |
| 净 MRR 变化 | 新增 MRR − 流失 MRR | 上述两项相减 | 收入健康度核心 |
| ARPU | 期末在服 MRR ÷ 期末在服用户数 | 相除 | 单位：元/用户/月 |
| 平均生命周期 | 期间流失记录的平均在服天数 | AVG(`churn_date` − `activation_date`) | 仅取期间流失样本 |
| LTV 估算 | ARPU ÷ 月流失率 | 相除 | 简化估算，报表中标注"估算值" |
| 环比增长率 | (本期 − 上期) ÷ 上期 | 指标自比 | 分母为 0 时显示"—" |
| 同比增长率 | (本期 − 去年同期) ÷ 去年同期 | 指标自比 | 数据不足 12 个月时显示"—" |

### 4.4 时间口径

| 项 | 约定 |
| --- | --- |
| 时区 | 统一按 `Asia/Shanghai`（中国无夏令时，避免跨时区歧义） |
| 日粒度 | 自然日，区间左闭右闭 |
| 周粒度 | 周一为一周首日 |
| 月粒度 | 自然月（1 日至月末） |
| 季度/年 | 自然季度、自然年 |
| 数据截止 | 当期末 23:59:59 |
| 未来日期 | 单据不支持"未来开通日期"（除计划生效日期外），避免污染存量计算 |

## 6. 功能需求

优先级说明：**P0 = 必须交付**；**P1 = 时间允许则交付，设计需预留**。

### FR-01 应用与模块脚手架（P0）

**描述**：通过 `bench new-app user_growth` 创建独立应用，并完成模块、依赖声明、hooks 配置与站点注册。

**验收要点**

- 应用可被 `bench --site <site> install-app user_growth` 成功安装，无残留报错。
- 应用目录结构符合 Frappe 标准（见设计文档第 4 章），模块名称在 Desk 中可见。

### FR-02 环境搭建与调试模式（P0）

**描述**：按文档可搭建可运行环境，并开启开发者模式以获得自动重载、脚本自动创建、错误全量展示等调试能力。

**验收要点**

- 站点配置中开发者模式已开启，新建/修改 Doctype 后无需手工迁移即可生效。
- 支持页面热重载（`bench watch` / `bench start`），前端代码修改后刷新即可见。
- 提供一条命令完成"启动服务"和"重启服务"，并在文档中给出常见故障排查清单。
- 演示环境默认站点、管理员账号、端口信息在文档中明确。

### FR-03 单据：用户服务记录（P0）

**描述**：建立核心业务单据，承载用户属性、地域、渠道、套餐与生命周期信息；同时支持"开通"与"流失"两类信息的表达。

**验收要点**

- 字段覆盖六类信息：用户属性、归属地域、获客渠道、套餐与商业、生命周期、流失信息。
- 记录编号按命名规则自动生成且不可重复。
- 支持同一终端客户的多段生命周期，可区分"首次开通"与"唤回"。
- 派生字段（生命周期天数、是否新客、状态）由系统自动计算，用户不可篡改。
- 状态与业务动作联动：填写流失信息后状态自动流转为"已流失"。

### FR-04 单据表单交互（P0）

**描述**：表单分区组织、条件显隐、即时校验、只读计算字段与状态可视化。

**验收要点**

- 表单按"用户与归属 / 服务与商业 / 生命周期与流失 / 备注与附件"分区，符合录入动线。
- 只有事件类型涉及流失/暂停时，才显示流失相关字段（避免干扰）。
- 非法输入（必填缺失、流失日期早于开通日期、金额为负、流失无原因）在保存时给出**指向具体字段**的中文提示。
- 列表页以颜色指示器区分状态（服务中 / 已流失 / 已暂停 / 待生效）。
- 只读计算字段有明确的样式差异，让用户知道"这不是我填的"。

### FR-05 单据列表与批量能力（P0）

**描述**：列表视图的可用性与批量数据处理能力。

**验收要点**

- 默认列聚焦决策信息（编号、用户、状态、开通日、流失日、套餐、渠道、大区、MRR）。
- 提供快捷筛选（状态、大区、渠道、套餐、时间区间）与关键字搜索（用户编号/名称）。
- 支持导出、支持按模板导入并提供**行级错误提示**（哪一行、哪个字段、什么原因）。
- 支持列表内批量修改状态/负责人（P1）。

### FR-06 权限与角色（P0）

**描述**：按角色分级授权，保证大屏与报表只读、单据可维护、配置仅管理员可见。

**验收要点**

- 至少 3 个角色：系统管理员、增长分析师（读写单+报表）、增长观察者（只读）。
- 观察者角色无法修改单据，但可查看报表与大屏。
- 手机号、邮箱等敏感字段按脱敏规则展示（字段级权限/格式化）。

### FR-07 Mock 数据生成（P0）

**描述**：一键生成覆盖 24 个月、具备真实分布特征的合成数据，供报表与大屏演示。

**验收要点**

- 单条命令生成，重复执行**幂等**（不产生重复脏数据），并提供可选"清空后重建"能力。
- 数据具备时间趋势（增长 + 季节性波动）与结构差异（渠道、区域、套餐、用户类型）。
- 流失率、客单价、生命周期分布符合设定的业务参数，并非均匀随机数。
- 生成过程有进度输出与结果摘要（生成条数、时间跨度、流失率、MRR 合计）。
- 生成脚本执行时间 < 10 秒（8,000 条规模）。
- 数据自检：无未来开通日期、无"流失早于开通"、无孤儿枚举值、金额非负。

### FR-08 报表：用户增长与流失分析（P0）

**描述**：以单据数据为基础的脚本报表，展示用户增长、流失与收入变化。

**验收要点**

- 支持时间粒度切换（日 / 周 / 月 / 季度 / 年）与自定义区间。
- 支持维度筛选（大区、省份、渠道、套餐、用户类型、计费周期、状态）与**按维度分组**输出。
- 默认输出列包含：期间、期初在服、新增、流失、净增长、期末在服、流失率、新增 MRR、流失 MRR、净 MRR、平均生命周期。
- 提供汇总行与环比/同比列。
- 顶部提供组合图表（柱：新增/流失，线：期末在服或流失率），随筛选条件联动。
- 支持导出 Excel/CSV；导出内容与屏幕展示一致。
- 报表内提供"指标口径说明"入口（避免评审追问口径时无法自证）。

### FR-09 报表扩展（P1）

**描述**：在原报表基础上提供下钻与专项分析能力。

**验收要点**

- 流失原因分布与流失原因 × 渠道交叉分析。
- 渠道质量分析（新增量、流失率、ARPU、LTV 估算排序）。
- 客户流失预警清单（健康分低 + 即将到期 + 高 MRR 优先级排序）。
- 新增报表以独立报表文件交付，不破坏 FR-08 的稳定性。

### FR-10 大屏页面（P0）

**描述**：以全屏方式展示用户分布与增长信息的可视化页面。

**验收要点**

- 单页展示 5 类信息：核心 KPI、用户增长趋势、用户地域分布、渠道/套餐结构、流失原因与重点客户。
- 1920×1080 无滚动条、无重叠；在 3840×2160 与 1366×768 下布局不破。
- 远距离可读：核心数字字号显著放大（1920 基准下 KPI 数字 ≥ 48px），对比度符合 WCAG AA。
- 无需人工操作即可长期运行：支持自动轮播/自动刷新并显示"最后更新时间"。
- 提供全屏按钮、时间范围切换、区域下钻等轻交互。
- 网络异常时显示友好提示与重试入口，不出现白屏。

### FR-11 大屏数据接口（P0）

**描述**：为大屏提供聚合数据的后端接口。

**验收要点**

- 一次请求即可返回首屏所需全部面板数据（减少请求数、降低大屏抖动）。
- 接口带参数校验、权限校验、超时与异常兜底。
- 支持短时缓存（同一分钟内重复请求不重复计算），并提供缓存开关。
- 接口返回结构包含时间戳与数据口径标识，便于前端展示"最后更新"。

### FR-12 数据刷新机制（P0）

**描述**：大屏数据的更新策略。

**验收要点**

- 默认 60 秒轮询刷新，刷新过程无整屏闪烁（局部更新 + 数字滚动过渡）。
- 提供手动刷新按钮与"暂停自动刷新"开关。
- 当数据量增大后，可切换为缓存 + 定时预计算策略（设计需预留）。

### FR-13 交付与演示脚本（P0）

**描述**：降低复现成本的一键脚本与演示流程。

**验收要点**

- 提供"环境初始化 → 安装应用 → 生成数据 → 启动服务"的可复制命令清单。
- 提供 5 分钟演示脚本（顺序、话术要点、预期画面）。
- 提供数据重置脚本（清空并重建 mock 数据）。

### FR-14 文档（P0）

**验收要点**

- 三份文档齐备：需求分析、可行性分析、详细设计。
- 文档包含指标口径、字段字典、权限矩阵、部署与排错说明。
- 文档与实现一致（字段名、报表列、接口路径可对照）。

### FR-15 增强项池（P1/P2）

| 编号 | 需求 | 优先级 | 说明 |

## 7. 非功能需求

### NFR-01 性能

| 编号 | 场景 | 指标 | 目标值 |
| --- | --- | --- | --- |
| NFR-01.1 | 报表查询（8,000 条、12 个月、月粒度） | 响应时间 | P95 ≤ 1.5s |
| NFR-01.2 | 报表查询（含分组透视、5 个维度） | 响应时间 | P95 ≤ 2.5s |
| NFR-01.3 | 大屏首屏（含图表渲染） | 完全可见时间 | ≤ 2.5s（局域网） |
| NFR-01.4 | 大屏刷新（只更新数据） | 接口耗时 | ≤ 800ms |
| NFR-01.5 | 单据列表首屏（20 条） | 响应时间 | ≤ 1s |
| NFR-01.6 | Mock 数据生成（8,000 条） | 执行时间 | ≤ 10s |

### NFR-02 容量与数据规模

- 本期数据规模：约 8,000 条服务记录，跨度 24 个月（可调参数 1,000 ~ 50,000 条）。
- 单表数据量增长到 100,000 条时，报表仍应可用（通过索引与聚合下推保证，设计文档给出方案）。

### NFR-03 可用性与容错

- 页面必须实现三态：加载中（骨架屏/进度提示）、空数据（引导文案）、异常（错误提示 + 重试）。
- 单个面板数据缺失不得导致整屏白屏（面板级降级）。
- 后端接口异常必须记录日志（含调用参数与堆栈），并返回可读的中文错误信息。

### NFR-04 兼容性

| 项 | 要求 |
| --- | --- |
| 浏览器 | Chrome / Edge ≥ 110，Firefox 最新版（大屏以 Chrome 为准） |
| 分辨率 | 1366×768 / 1920×1080 / 2560×1440 / 3840×2160 |
| 服务端 | Frappe v15 基线（Python / MariaDB / Redis 版本见设计文档第 2 章） |
| 网络 | **必须支持纯内网/离线运行**，不依赖外部 CDN 加载图表库或字体 |

### NFR-05 安全与隐私

- 所有后端接口需登录态校验，大屏匿名访问默认关闭（如开启需限制为只读且仅返回聚合数据）。
- 敏感字段（手机号、邮箱）在界面与导出中按规则脱敏：`138****1234`、`a***@example.com`。
- 报表/大屏仅提供聚合与只读视图，不暴露明细级 PII。
- 数据库查询必须参数化，禁止拼接用户输入（防 SQL 注入）。
- 关键字段变更留痕（记录变更历史），保证"谁在什么时候改了流失原因"可追溯。

### NFR-06 可维护性与代码规范

- 遵循 Frappe 官方约定：业务逻辑放 DocType 控制器，报表逻辑放 `execute()`，页面逻辑放标准页面脚本。
- 无自定义构建工具链，不引入 Vue/React 等额外前端框架复杂度（大屏图表库为唯一前端依赖，且本地打包）。
- 计算逻辑集中：报表与大屏共用同一套口径实现，禁止两处各写一套 SQL。
- 关键逻辑有注释与单元测试（至少覆盖校验规则与指标计算）。

### NFR-07 可运维性

- 提供应用卸载与数据清理说明（`uninstall-app` 行为、数据保留策略）。
- mock 数据脚本可重复执行、可回滚（清空重建）。
- 提供日志位置、常见错误码与排查步骤。

### NFR-08 国际化与本地化

- 界面文案以中文为主，字段标签全部通过翻译函数包裹，便于后续输出英文版本。
- 数字使用千分位分隔、金额保留 2 位小数、百分比保留 1~2 位小数；日期显示为 `YYYY-MM-DD`。

### NFR-09 可访问性与色彩无障碍

- 大屏不依赖"红 = 坏 / 绿 = 好"的单一色相区分，同时使用图标、方向箭头或数值符号。
- 正文对比度 ≥ 4.5:1，大字 ≥ 3:1；提供"高对比模式"或至少在设计规范中锁定安全色值。
- 动效尊重系统"减少动态效果"偏好（动画可关闭）。
- 报表支持键盘导航与表头语义。

### NFR-10 可测试性

- DocType 校验规则、派生字段、指标计算具备单元测试；报表可用固定数据集做结果断言。
- 提供测试数据生成器与一键清库，保证测试环境可重复。

### NFR-11 离线与内网可用

- 图表库、字体、图标全部随应用静态资源打包，通过 `bench build` 产出。
- 无外部接口调用；首次安装后即可断网演示。

## 8. 数据需求

### 8.1 数据来源

本期数据全部为**合成 mock 数据**，由应用内置生成器产生，不使用任何真实客户信息。字段设计按真实业务场景建模，便于后续替换为真实数据源。

### 8.2 数据规模与分布要求

| 维度 | 要求 |
| --- | --- |
| 时间跨度 | 24 个月（含当前月），支持参数化 |
| 记录总量 | 默认约 8,000 条（可调 1,000 ~ 50,000） |
| 时间分布 | 整体上升趋势 + 季节性波动（春节低谷、年中促销、年末冲高） |
| 大区分布 | 华东 > 华南 > 华北 > 华中 > 西南 > 西北 > 东北 > 海外（按权重） |
| 渠道分布 | 官网直销、内容营销、搜索广告、信息流、合作伙伴、代理商、线下活动、老客推荐、自然流量 |
| 套餐分布 | 免费试用、基础版、专业版、企业版、旗舰版、定制版（占比递减） |
| 流失分布 | 月流失率 2%~6% 波动，与套餐/渠道/用户类型相关（低价套餐与信息流渠道流失更高） |
| 生命周期 | 免费试用偏短（7~30 天），企业版偏长（≥ 365 天） |
| 金额 | 与套餐、计费周期、折扣率联动，MRR 按计费周期折算 |

### 8.3 业务字段需求（业务视角）

| 分组 | 需要被记录的信息 |
| --- | --- |
| 用户属性 | 用户唯一标识、用户名称、用户类型（个人/团队/企业）、所属行业 |
| 归属地域 | 国家、省份、城市、大区 |
| 获客渠道 | 渠道分类、细分来源、活动/活动编号 |
| 服务与商业 | 套餐、计费周期、合同金额、币种、月费（MRR）、折扣 |
| 生命周期 | 首次开通日、本次开通日、生效日、上次续费日、到期日、流失日、生命周期天数、生命周期序号 |
| 流失信息 | 是否流失、流失类型、流失原因、是否可唤回、健康分、挽回备注 |
| 责任与协作 | 服务负责人、关联工单号、备注、附件 |
| 系统信息 | 记录编号、创建/修改人、创建/修改时间、数据来源标识 |

### 8.4 数据质量要求

1. 必填字段不得为空；枚举字段取值必须来自受控列表。
2. 日期关系合法：开通日 ≤ 生效日 ≤ 到期日；流失日 ≥ 开通日；不得出现未来开通日期。
3. 金额非负；折扣率 0~100%；健康分 0~100。
4. 同一终端客户的多段生命周期必须有明确序号，且时间段不重叠。
5. 记录编号唯一；同一用户的同一开通日不允许重复。

### 8.5 隐私与合规

- 合成数据不得与真实个人关联；姓名、手机号、邮箱均为生成值。
- 即便为合成数据，字段设计中仍保留脱敏展示规则，以验证真实场景下的合规能力。
- 附件与备注字段提示使用者不要上传含个人敏感信息的文件。

## 9. 交互与体验需求（概要）

详细交互规格见《详细设计文档》第 8、9 章；本章只锁定体验目标。

### 9.1 三端定位差异

| 交付物 | 使用者 | 阅读距离 | 信息密度 | 交互复杂度 | 核心体验目标 |
| --- | --- | --- | --- | --- | --- |
| 单据表单 | 运营/客户成功专员 | 50cm | 高（多字段） | 高（录入/校验） | 录入快、错不了、看得懂 |
| 报表 | 数据分析师 | 60cm | 极高（表格） | 高（筛选/分组/导出） | 筛选顺手、口径可信、导出可用 |
| 大屏 | 管理者/评审 | 3~8m | 低（少而大） | 低（自动运行） | 一眼看懂、不用操作、稳定运行 |

### 9.2 通用体验原则

1. **三态完备**：加载、空数据、错误均有明确界面，不出现空白与转圈卡死。
2. **即时反馈**：保存、导出、刷新、生成数据均有进度或结果提示。
3. **防错优先**：默认值合理、危险操作二次确认、批量操作前告知影响范围。
4. **一致性**：颜色语义（增长/流失/中性）、数字格式、术语在单据、报表、大屏之间完全一致。
5. **性能感知**：超过 300ms 的操作必须有加载反馈；大屏刷新采用局部更新避免闪烁。

### 9.3 大屏专项体验要求

- **视觉层级**：核心数字 > 趋势图 > 分布图 > 明细榜单，形成清晰的阅读顺序（先看结论，再看原因）。
- **远距离可读**：字号、对比度、图形粗细按"3 米外可读"标准设计；避免细线与小字说明。
- **信息自证**：每个面板标注指标口径/单位/时间范围，避免"数字好看但不知道是什么"。
- **持续运行**：自动刷新 + 自动轮播 + 异常自恢复；显示"最后更新时间"，避免展示过期数据。
- **无操作依赖**：所有关键信息在默认态即可见，交互仅作为加分项而非必需品。
