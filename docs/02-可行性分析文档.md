## 1. 文档目的与结论摘要

### 1.1 目的

本文档回答"这件事能不能做成、要花多大代价、最大的坑在哪里"。评估对象是《需求分析文档》中定义的 S1~S6 范围，判断维度包括：技术、环境、数据、工期、成本、风险。所有结论都对应到可验证的证据或可复现的验证动作，而非主观判断。

### 1.2 结论摘要

| 评估维度 | 结论 | 关键依据 |
| --- | --- | --- |
| 技术可行性 | **高** | 需求的三项交付物均为 Frappe 原生能力覆盖（Doctype / Script Report / Page + 白名单接口），无需自研框架 |
| 环境可行性 | **中高（需注意 OS 约束）** | Frappe 官方不支持 Windows 原生运行；本项目宿主为 Windows，需通过 WSL2 或 Docker 承载，属已知且成熟的路径 |
| 数据可行性 | **高** | 全部为合成数据，规模（约 8,000 条）远低于性能压力阈值，分布可通过参数化生成器控制 |
| 进度可行性 | **高** | 主要工作量集中在报表与大屏的前端呈现，核心路径约 7~9 人日，可分解为可独立验收的里程碑 |
| 成本可行性 | **高** | 全栈开源，零许可成本；仅消耗本地算力与网络流量 |
| 风险可行性 | **可控** | 已识别 10 项风险，其中 2 项为高关注（Windows 环境、大屏全屏呈现），均有明确缓解方案 |

**总体结论：项目可行，建议进入实施。** 实施前需完成第 10 章的 6 项前置条件（尤其是运行环境选型与流失率口径冻结）。

## 2. 技术可行性

### 2.1 需求 → 框架能力映射

逐条验证"需求是否落在框架能力范围内"，是技术可行性的核心证据。

| 需求编号 | 需求内容 | Frappe 原生能力 | 可行性判断 | 验证方式 |
| --- | --- | --- | --- | --- |
| FR-01 | 自定义 App 脚手架 | `bench new-app`、`apps.txt` 注册、`hooks.py` | 完全覆盖 | 执行命令后检查目录与站点应用列表 |
| FR-02 | 调试模式与热重载 | `site_config.json` 中开启开发者模式、`bench start`（含 watch 进程）、错误全量回显 | 完全覆盖 | 修改前端资源后刷新浏览器验证 |
| FR-03 | 业务单据 | DocType（字段、命名规则、索引、权限、控制器） | 完全覆盖 | 新建/保存/查询验证 |
| FR-04 | 表单交互 | 表单脚本（条件显隐、只读、校验、状态指示、栅格布局） | 完全覆盖 | 构造非法输入验证拦截与提示 |
| FR-05 | 列表与批量 | 列表视图配置、默认筛选、导入导出、批量操作 | 完全覆盖 | 导入含错误的文件验证行级报错 |
| FR-06 | 权限角色 | Role、DocPerm、字段级权限、查询条件权限 | 完全覆盖 | 多角色账号回归 |
| FR-07 | Mock 数据 | 独立生成脚本 + `bench execute`、安装钩子、批量写入 API | 完全覆盖 | 连续执行两次比对条数（幂等） |
| FR-08 | 分析报表 | Script Report（后端聚合 + 前端筛选器 + 图表 + 导出） | 完全覆盖 | 抽样核对报表结果与 SQL 直算结果 |
| FR-09 | 下钻类扩展 | 追加报表文件 / 报表内分组参数 | 完全覆盖 | 独立报表可单独访问 |
| FR-10 | 大屏页面 | 标准 Page（HTML + 脚本）或应用内 Web 页面路由 | **覆盖，但需注意呈现细节**（见 2.4） | 4 种分辨率下实机投屏检查 |
| FR-11 | 聚合接口 | 白名单方法与缓存 API | 完全覆盖 | 浏览器网络面板确认请求数 |
| FR-12 | 刷新机制 | 前端定时器 + 框架实时通道（可选） | 完全覆盖 | 挂屏 30 分钟观察 |
| FR-13/14 | 脚本与文档 | `bench` 命令链 + 仓库文档 | 完全覆盖 | 全新环境复现 |

**结论**：13 条 P0 功能需求中，12 条为框架"开箱能力"，1 条（大屏）为"能力覆盖但需设计技巧"。技术上不存在需要自研底层设施的部分，可行性高。

### 2.2 关键技术点论证

#### 2.2.1 指标计算能否高效实现？

《需求分析文档》4.3 定义的 16 项指标，本质是两类查询：

1. **期间事件计数**（新增、流失、MRR 变动）：`GROUP BY` 时间桶 + 维度过滤，是最基础的聚合查询。
2. **时点存量计数**（期初/期末在服、平均在服）：属于"区间重叠计数"，用 `activation_date <= T AND (churn_date IS NULL OR churn_date > T)` 表达，配合 `(activation_date, churn_date)` 复合索引可高效执行。

在 8,000 条规模下，两类查询都在毫秒级；即便增长到 10 万条，单月聚合仍是索引范围扫描，不会退化为全表扫描。**结论：无需预计算表/物化视图即可满足本期性能目标**，预计算作为 P1 演进项保留（设计文档 7.5、8.8 节）。

#### 2.2.2 报表与大屏能否共用同一套口径？

能，且**必须**。做法是把口径计算下沉到应用的业务逻辑层（统一的时间桶/区间重叠/流失率函数），报表脚本与大屏接口都调用它。这既避免了"两处各写一套 SQL 导致数字对不上"的经典事故，也让口径变更只需改一处。这也直接回应了考核点中的"需求分析及理解"——口径一致性是增长类需求最容易出问题的地方。

#### 2.2.3 大屏的可视化实现是否依赖外部服务？

不依赖。图表能力由应用自带的静态资源提供（随 `bench build` 打包），地图/地理分布可采用"省份条形排行 + 区域热力"或内嵌地图数据两种方式，**即使不引入外部地图服务也能满足"用户分布"展示**。这一点对本项目至关重要，因为 NFR-11 要求纯内网可演示。（图表库的具体选型见设计文档 9.4。）

#### 2.2.4 mock 数据的"真实性"能否达到演示要求？

可以。生成器按"参数化分布 + 季节性系数 + 生命周期建模"生成，能够呈现：整体上升趋势、明显的季节波动、渠道/套餐结构差异、与套餐相关的流失率差异、以及由此自然形成的"某渠道新增多但留存差"等可讲述的业务洞察。相比均匀随机数，这种数据在评审时能支撑"数据 → 结论"的完整叙事。

### 2.3 技术约束与兼容性

| 约束 | 说明 | 应对 |
| --- | --- | --- |
| 框架版本 | 大版本间存在 API 差异（页面/报表图表/工作区等） | 锁定 v15 基线；设计中标注需要版本适配的点 |
| 运行宿主 | 官方不支持 Windows 原生部署 | 采用 WSL2 或 Docker（见第 4 章） |
| 前端技术栈 | 避免引入重型框架造成维护复杂度 | 原生 JS + 单图表库，逻辑集中在页面脚本 |
| 数据库 | MariaDB 版本需满足框架最低要求 | 使用框架官方支持的发行版镜像 |
| 依赖下载 | 首次搭建需要联网拉取依赖 | 预配置国内镜像源，预留搭建时间 |

### 2.4 交互设计的可行性（考核点 3）

这是本项目中**风险最集中**的一环，也是最能体现交付质量的一环。逐项论证：

| 体验目标 | 可行性 | 说明与风险 |
| --- | --- | --- |
| 大屏 1920×1080 无滚动条、远距离可读 | 可行 | 采用固定基准分辨率 + 等比缩放容器方案，配合浅色高对比配色（文字对比度由脚本断言，正文 ≥ 4.5:1）；风险在于不同设备的缩放设置，需在验收表里锁定测试机型 |
| 大屏长期挂屏稳定 | 可行 | 定时刷新 + 面板级降级 + 内存回收（避免长时间运行后内存增长） |
| 大屏脱离 Desk 边框的沉浸感 | **部分受限** | 标准 Page 运行在 Desk 容器内，需要隐藏侧边栏/顶栏并锁定全宽布局；若追求极致沉浸，可用应用内 Web 页面路由作为备选路径（设计文档 9.1 给出两方案对比与选择） |
| 报表筛选与分组体验 | 可行 | 框架原生筛选器 + 分组参数即可实现，重点在默认值与快捷预设的合理设计 |
| 表单录入效率 | 可行 | 分区 + 条件显隐 + 即时校验，均为框架原生能力 |

**结论**：交互设计目标整体可达；"大屏沉浸感"是实现细节风险而非能力缺失，已给出缓解方案与备选路径。

## 3. 数据可行性

### 3.1 规模与性能测算

| 规模 | 单月聚合耗时（估算） | 单次大屏接口耗时（估算） | 说明 |
| --- | --- | --- | --- |
| 8,000 条（本期默认） | < 50ms | < 300ms | 远优于 NFR 目标 |
| 50,000 条 | 100~300ms | 0.5~1.2s | 仍需满足目标，建议加缓存 |
| 200,000 条 | 300ms~1s | 1~3s | 建议启用预计算快照表（P1） |

> 上表为基于"索引 + 聚合下推"的工程估算，实施阶段会以真实数据实测并回填（设计文档 13 章给出测量方法）。

### 3.2 数据质量可控性

合成数据天然满足"可重复、可自检、可回滚"：生成器内置自检断言（无未来日期、无流失早于开通、枚举受控、金额非负、生命周期序号不重叠），执行后输出质量报告。这意味着**演示数据的正确性不依赖人工核对**。

### 3.3 隐私与合规

- 数据 100% 合成，不涉及真实个人信息，规避《个人信息保护法》下的采集与处理义务。
- 字段设计中保留脱敏展示规则，用于验证真实场景的合规处理能力（掩码规则见设计文档 11.2）。
- 附件、备注字段在界面给出合规提示。

## 4. 环境可行性

### 4.1 关键结论：Windows 宿主需要间接方案

Frappe 的官方运行方式以 Linux 为目标环境（依赖 Python 运行时、MariaDB、Redis、Node 构建链、`bench` 命令行、系统级进程管理）。当前开发宿主为 Windows，因此**必须**选择以下三种承载方式之一：

| 方案 | 实现方式 | 优点 | 缺点 | 适用场景 | 推荐度 |
| --- | --- | --- | --- | --- | --- |
| A. WSL2 + Ubuntu | 在 Windows 内启用 WSL2，安装 Ubuntu 发行版，在其中按官方方式搭建 | 与官方文档完全一致；调试体验接近原生 Linux；文件系统性能好（把工程放在 WSL 文件系统内） | 需启用虚拟化与 WSL 功能；首次安装耗时长 | 需要深入调试框架、长期开发 | ★★★★★ |
| B. 容器化 | 使用官方容器化方案（compose 方式）拉起框架与依赖服务 | 环境一致、可复现、一条命令起全套；跨机器迁移容易 | 需要 Docker Desktop/WSL2 后端；镜像拉取需要网络；调试需进入容器 | 追求"开箱即用"与可复现交付 | ★★★★☆ |
| C. 远程 Linux 主机 | 在虚拟机或云主机上部署，本地通过浏览器访问 | 完全不依赖本地性能 | 需要额外机器/成本；网络依赖 | 本地资源不足时的备选 | ★★★☆☆ |

**建议**：以 **A（WSL2）为主**，把 **B（容器化）作为可复现交付的备选**。两者都要求在 Windows 侧先启用虚拟化与 WSL2，这一步是必须的成本，无法绕过。

### 4.2 依赖与资源需求

| 类别 | 需求 | 说明 |
| --- | --- | --- |
| 运行时 | Python（框架要求的最低版本及以上） | 由发行版或容器提供，避免使用系统 Python 直接安装 |
| 数据库 | MariaDB（框架支持版本） | WSL 中独立服务或容器服务 |
| 缓存/队列 | Redis | 框架必需组件 |
| 构建 | Node.js + 包管理器 | 用于前端资源构建 |
| 命令行 | `bench` CLI | 框架统一入口 |
| 磁盘 | 建议 ≥ 15GB 可用空间 | 依赖包 + 数据库 + 构建产物 |
| 内存 | 建议 ≥ 8GB（16GB 更稳） | 数据库 + Redis + 构建进程 |
| 网络 | 首次搭建需要访问包源与代码托管站 | 建议配置国内镜像加速 |

### 4.3 搭建与调试模式的可行性

"快速搭建框架并启用调试模式"是本项目的考核点之一，其可行性建立在 **步骤确定性** 上：

| 步骤 | 动作 | 预期耗时（估算） | 失败时的排查点 |
| --- | --- | --- | --- |
| 1 | 启用 WSL2 并安装发行版 | 10~30 分钟 | 虚拟化未开启、需要重启 |
| 2 | 安装系统依赖（数据库、缓存、运行时、构建工具） | 10~20 分钟 | 包源慢、版本不匹配 |
| 3 | 初始化 bench 环境 | 10~30 分钟 | 依赖下载慢/失败，需配置镜像 |
| 4 | 创建站点并安装应用 | 5~10 分钟 | 数据库认证、管理员密码 |
| 5 | 开启开发者模式并启动服务 | 2~5 分钟 | 端口占用、缓存未清 |

**调试模式的价值（必须显式说明，因为它直接决定后续开发效率）**：

1. 修改 Doctype / 报表 / 页面后无需手工迁移即可生效，缩短"改—看"循环。
2. 前端资源支持热重载，样式与脚本改动刷新即可见。
3. 错误与堆栈完整回显到浏览器与日志，便于定位。
4. 可通过交互式控制台直接执行后端逻辑，快速验证数据与口径。

> 结论：搭建路径明确、步骤可脚本化，可行性高；唯一的不确定性来自首次依赖下载，属于"时间成本"而非"能力风险"，已通过预留时间与镜像源配置缓解。

### 4.4 交付可复现性

为保证"评审人能在自己机器上复现"，交付物需要包含：环境搭建命令清单、应用安装命令、数据生成命令、启动命令、演示脚本、常见故障排查表。这些内容在设计文档第 13、15 章给出版本化清单。

| --- | --- | --- |

| 砍 35% | 报表暂不做分组透视与同比；大屏取消下钻 | 分析深度下降，核心结论仍可呈现 |
| 砍 50% | 只交付单据 + 报表 + 最小可用大屏（3 面板） | 满足三项交付物的最低要求 |

> 降级顺序原则：**先砍增强项（P1），再砍交互深度，最后才砍面板数量**，始终保住"三项交付物均可用且数据一致"这条底线。

## 8. 替代方案对比

在"用 Frappe 完成"这一前提下，实现路线仍有三种选择：

| 对比维度 | 方案 A：原生能力优先（推荐） | 方案 B：自定义前端框架 | 方案 C：外接 BI 工具 |
| --- | --- | --- | --- |
| 大屏实现 | 标准页面 + 原生 JS + 图表库 | 独立 SPA（Vue/React）嵌入 | BI 工具（如外部仪表盘） |
| 单据与报表 | 框架原生 Doctype / Script Report | 自定义接口重建 | 依赖外部数据同步 |
| 开发工作量 | 中低 | 高 | 中，但引入外部系统与部署成本 |
| 与框架契合度 | 高，升级兼容性好 | 低，需自行处理权限/主题/构建 | 低，数据授权割裂 |
| 可维护性 | 高，符合平台约定 | 中，多一套构建链与依赖 | 低，跨系统排查 |
| 离线可演示 | 是 | 是（需打包） | 通常否 |
| 交互上限 | 高（可做全屏定制） | 最高 | 受工具限制 |
| 风险 | 低 | 中高（时间、依赖、主题冲突） | 高（许可、部署、数据隔离） |
| 评分（满分 5） | **4.6** | 3.6 | 2.8 |

**结论：采用方案 A。** 理由：三项交付物均在框架原生能力范围内，原生路线在权限、主题一致性、升级兼容与交付成本上全面占优；仅在"大屏沉浸感"这一单点上，用设计技巧补足即可，无需为此引入整套前端工程化设施（符合"以最小代价达成目标"的工程原则）。

## 10. 可行性结论与实施前置条件

### 10.1 结论

1. **技术可行**：三项交付物均为框架原生能力覆盖，无自研底层设施需求；唯一需要设计技巧的是大屏呈现，已有明确方案与备选路径。
2. **环境可行**：Windows 宿主是唯一需要额外处理的约束，WSL2 与容器化两条成熟路径均可满足；调试模式的价值明确且易于启用。
3. **数据可行**：合成数据规模小、质量可控、合规风险低，且能通过参数化生成支撑"可讲述"的业务叙事。
4. **进度可行**：约 7~10 人日，关键路径清晰，具备可裁剪的降级策略。
5. **成本可行**：零许可成本，仅消耗本地资源与人力。
6. **风险可控**：10 项风险全部识别，4 项高关注风险均有"首次验证时间点 + 通过标准"。

**建议：批准立项，按第 5.2 节里程碑推进，并优先执行 R-01、R-02、R-04 三项前置验证。**

### 10.2 实施前置条件检查表

| --- | --- | --- | --- |

### 10.3 可行性结论的复核点

以下情况下需要重新评估可行性：数据规模超过 20 万条、需要接入真实数据源、要求多租户或生产级高可用、需要英文/多语言正式交付、要求大屏支持触控交互。这些均属于本期范围之外，若提出需重新走本文档的评估流程。
