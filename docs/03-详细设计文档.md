## 1. 设计目标与原则

### 1.1 设计目标

| 目标 | 说明 | 对应需求 |
| --- | --- | --- |
| 三项交付物完整可用 | 单据、报表、大屏全部可用且数据一致 | FR-03/08/10 |
| 口径单一可信 | 所有指标只有一处实现，报表与大屏结果必须完全一致 | NFR-06, R-05 |
| 交付可复现 | 新机器按文档可一次跑通：环境 → 应用 → 数据 → 页面 | FR-01/02/13 |
| 交互达演示级质量 | 大屏远距离可读、报表顺手、表单不易出错 | FR-04/10, NFR-09 |
| 可演进 | 数据量增长、接入真实数据、扩展分析维度时不需要重写 | NFR-02, FR-15 |

### 1.2 设计原则

1. **原生优先（约定优于配置）**：能用框架标准能力解决的，不引入自定义设施；只在框架能力不足的"大屏沉浸感"单点上做最小化定制。
2. **单一事实来源**：口径计算集中在 `analytics` 层一处实现，报表脚本与大屏接口只做"取数 + 编排"。
3. **数据即文档**：字段标签、枚举选项、指标说明直接写进系统（表单提示、报表口径说明、大屏状态栏），让使用者不依赖口头交接。
4. **性能前置**：索引、参数化查询、缓存策略在设计阶段确定，不留到最后调优。
5. **可降级**：大屏面板级降级、报表分组可选、无地图时退化为条形排行——任何单点缺失都不能导致整页不可用。
6. **尊重使用者注意力**：一屏给一个结论；颜色、字号、位置都服务于"先看结论，再看原因"。

## 2. 版本与环境基线

### 2.1 版本基线

| 组件 | 基线选择 | 说明 |
| --- | --- | --- |
| Frappe Framework | v15 系列（生产稳定版） | 需求涉及的全部能力（DocType / Script Report / Page / 白名单接口 / 静态资源打包）均已具备 |
| Python | 框架 v15 要求的 3.10+ | 由发行版或容器镜像提供 |
| 数据库 | 框架支持的 MariaDB 版本 | 需支持窗口函数（可选优化项） |
| 缓存/队列 | Redis | 框架必需组件 |
| 构建 | Node.js + 包管理器 | 用于 `bench build` 产出静态资源 |
| 可视化实现 | **应用内自绘 SVG 图表**（零第三方依赖） | 大屏只用到 4 种图形；自绘可完全离线、无许可与版本风险，且视觉令牌（配色/字号/间距）完全可控 |
| 操作系统 | WSL2（Ubuntu LTS）为主，容器化为备选 | 见《可行性分析文档》第 4 章 |

### 2.2 兼容性说明（v15 → 后续大版本需关注的点）

| 关注点 | 说明 | 应对 |
| --- | --- | --- |
| 页面（Page）元数据字段 | 不同大版本对标准页面元数据字段的组织可能调整 | 实现前通过控制台读取实际 Doctype 元数据确认字段名 |
| 报表图表配置 | 报表内嵌图表的配置项在不同版本可能变化 | 图表以报表页前端脚本实现，避免强依赖元数据字段 |
| Desk 前端组件 | 顶栏/侧边栏的类名与结构可能变化 | 沉浸模式通过 CSS 类切换实现，并把类名集中在一个配置对象中便于适配 |
| 权限与角色 | 权限模型总体稳定 | 使用标准权限 API，不直连权限表 |
| 静态资源打包 | 机制稳定 | 使用 `bench build --app` 标准流程 |

> 版本适配原则：把"可能变化的外部依赖"收敛到 3 个位置（页面元数据、Desk 类名、报表图表配置）并集中配置，避免散落各处。

### 2.3 环境准备步骤（设计层面的标准流程）

| 步骤 | 命令形态（示意） | 设计要点 |
| --- | --- | --- |
| 1. 初始化工作目录 | `bench init <bench-dir> --frappe-branch <版本分支>` | 目录放在 Linux 文件系统内，避免跨系统文件访问的性能损耗 |
| 2. 创建站点 | `bench new-site <site-name>` | 记录数据库与管理员凭据 |
| 3. 创建应用 | `bench new-app user_growth` | 应用名与模块名在本设计第 4、5 章固定 |
| 4. 安装应用 | `bench --site <site> install-app user_growth` | 安装后立即验证模块可见 |
| 5. 开启开发者模式 | `bench --site <site> set-config developer_mode 1` | 考核点 1 的落点：自动重载、脚本自动生成、错误全量回显 |
| 6. 启动服务 | `bench start` | 同时拉起 Web、Socket、资源监听、定时与后台任务进程 |
| 7. 生成数据 | `bench --site <site> execute <seed 入口>` | 幂等，可重复执行 |

**调试模式带来三项直接收益**（必须在交付说明中写明）：

1. 修改报表/页面脚本后刷新即生效，不需要反复迁移。
2. 前端资源改动由监听进程自动重建。
3. 服务端异常堆栈完整回显，便于快速定位。

**排错清单（写入交付文档）**：页面 404（资源未构建或应用未安装）、白屏（脚本语法错误，查看浏览器控制台）、权限拒绝（角色未授权）、数据为空（未执行数据生成或筛选区间无数据）、端口被占用（更换端口启动）。

## 3. 总体架构

### 3.1 运行架构

```
┌──────────────────────────── 浏览器 ────────────────────────────┐
│  单据表单/列表 (Desk)   报表页面 (Desk)   增长大屏 (Page)      │
└───────────────┬──────────────────┬─────────────────┬──────────┘
                │ REST/JSON        │ 报表执行         │ 白名单接口
┌───────────────▼──────────────────▼─────────────────▼──────────┐
│                   Frappe 应用层（user_growth）                 │
│  DocType 控制器   报表脚本   页面脚本   白名单接口   ★口径层    │
│  (校验/派生)      (编排)     (视图)     (聚合/缓存)  analytics  │
└───────────────┬──────────────────┬─────────────────┬──────────┘
                │                  │                 │
       ┌────────▼───────┐  ┌───────▼───────┐  ┌──────▼───────┐
       │  MariaDB       │  │  Redis        │  │  静态资源     │
       │  服务记录表    │  │  聚合结果缓存  │  │  图表库/样式  │
       └────────────────┘  └───────────────┘  └──────────────┘
```

### 3.2 应用内分层

| 层 | 位置 | 职责 | 不做什么 |
| --- | --- | --- | --- |
| 数据层 | DocType（含控制器） | 字段、约束、派生字段、生命周期状态、权限 | 不做展示格式化 |
| 口径层 | `analytics/` 模块 | 时间桶、区间重叠计数、流失率、MRR、生命周期等唯一实现 | 不直接面向界面 |
| 编排层 | 报表的 `execute()`、大屏接口 | 参数解析与校验 → 调口径层 → 组装目标结构 | 不写独立 SQL 口径 |
| 展示层 | 报表页脚本、页面脚本 | 渲染、交互、格式化、状态处理 | 不参与指标计算 |
| 数据准备层 | `seed/` 模块 | 参数化生成 mock 数据、幂等、自检 | 不写业务校验（复用 DocType 控制器） |

> 设计要点：口径层是整个设计的心脏。"报表与大屏数字必须对得上"这条硬约束，靠的不是测试，而是结构——两者共用同一个函数。

| 对象 | 规范 | 示例 |
| --- | --- | --- |
| 应用名 | 小写 + 下划线 | `user_growth` |

| DocType 名 | 英文单数、首字母大写 | `User Service Record` |
| 字段名 | 小写 + 下划线，语义清晰 | `churn_reason_category` |
| 字段标签 | 中文业务术语 | 流失原因分类 |
| 报表名 | 业务可读 | 用户增长与流失分析 |
| 页面名 | 小写 + 下划线，路由以连字符呈现 | `growth_dashboard` → `/app/growth-dashboard` |
| 接口名 | 动词 + 名词 | `get_dashboard_data` |
| 枚举值 | 中文业务值（受控列表，集中定义） | 已流失 |
| 时间字段 | 以 `_date` 结尾表示为日期 | `activation_date` |
| 金额字段 | 明确单位与口径 | `mrr`（元/月） |

**强约束**

1. 任何 SQL 必须参数化，禁止字符串拼接用户输入。
2. 枚举值只允许出现在一处（口径层或字段定义），报表与大屏脚本不得硬编码重复列表。
3. 面向用户的文案全部走翻译函数包裹，为后续英文版留出空间。
4. 前端脚本禁止内联大段 HTML 与业务口径计算，口径一律来自接口。

## 6. 数据模型设计

### 6.1 设计决策记录（ADR-001）：记录语义

| 维度 | 方案 A：事件型（每次动作一行） | 方案 B：生命周期型（一段订阅一行，采纳） |
| --- | --- | --- |
| 表达"开通/流失" | 需要两行（开通行 + 流失行）关联 | 一行内同时表达 |
| 期末在服数 | 需要累计 + 去重（子查询/窗口） | 一行条件判断：`activation_date ≤ T < churn_date` |
| 流失率 | 需按事件聚合 | 直接计数 |
| 平均生命周期 | 需跨行配对 | 直接字段相减 |
| 续费过程 | 天然支持 | 需子表补充 |
| 结论 | 灵活但复杂、性能差 | 贴合需求、口径简单、性能好；续费用 P1 子表补齐 |

**决策**：采用方案 B，用 `lifecycle_seq`（生命周期序号）表达同一用户的第 N 段服务，用 `is_winback` 表达唤回。

**查询优化原则**

1. 时间条件必须下推到数据库，禁止把全表取回后在应用层过滤。

3. 期间类与存量类指标分别查询后合并，避免用复杂 JOIN 表达。
4. 需要某一时点的存量时使用左闭右开表达：`activation_date < T AND (churn_date IS NULL OR churn_date >= T)`。

**状态机（优先级从高到低）**

```
如果有流失日期                    → 已流失
否则如果今天小于服务生效日期        → 待生效
否则如果标记为暂停                 → 已暂停
否则如果存在到期日且今天大于到期日  → 已到期
否则                              → 服务中
```

> "已暂停"由业务动作显式标记（P1 子表或手工字段）而非自动推导，避免把暂停误算为流失——《需求分析文档》Q-05 已锁定该口径。

### 7.4 生成算法（伪代码）

```
固定随机种子

for 每个月份 M in 最近 24 个月:
    基础新增量 = 基准值 × 年度增长系数(M) × 季节性系数(M 月) × 随机扰动(±8%)
    for 每条新开通记录:
        按权重抽样：大区 → 省份（省内按权重） → 城市
        按权重抽样：渠道、用户类型、客户分层、套餐、计费周期
        合同金额 = 标准月费 × 计费月数 × (1 − 折扣率)
        计算 MRR 与健康分（基线 82 + 套餐修正 + 随机噪声，截断 30~99）
        开通日期 = 该月内随机日（与季节系数正相关）

    for 每条已开通且未流失的记录:
        实际月流失率 = 套餐基线流失率 × 渠道系数 × 客户类型系数
        以该概率判定本月是否流失
        若流失:
            流失日期 = 本月内随机日（不早于开通日）
            抽取流失类型与原因分类（试用结束仅限免费套餐；竞品替换生成竞品名）
            按原因与套餐下调健康分
        若流失且该用户不在不可唤回名单:
            以唤回概率在流失后 30~180 天生成第二段生命周期
            （生命周期序号加 1，首次开通日期继承，上次流失日期回填）

分批批量写入数据库
运行数据自检并输出质量报告
```

**关键设计点**

1. **先开通、后流失**：按时间顺序推进，天然保证"流失日期不早于开通日期"，不依赖事后再修。
2. **参数化而非硬编码**：所有分布参数集中在分布参数文件，调整数据风格不需要改算法。
3. **可讲述性**：季节性、渠道质量差异、套餐分层是刻意设计的，目的是让大屏与报表能得出有意义结论。

### 7.5 幂等、执行与性能

### 8.1 交付形态

### 8.3 输出列定义（不分组模式）

**共 14 列，列宽合计约 1250px**（常见笔记本屏不横向滚动）。列宽与类型必须同时满足"能读"与"能比"：
用对字段类型，让框架按类型格式化，而不是靠列名写单位。

| 列 | Frappe 字段类型 | 宽度 | 渲染效果 | 计算口径 |
| --- | --- | --- | --- | --- |
| 期间 | Data | 100 | `2026-10` / `2026-W41` | 按粒度格式化的时间桶标签 |
| 期初在服 | Float(precision=0) | 84 | `2,528` | 时点存量（区间重叠法） |
| 新增 | Float(precision=0) | 76 | `394` | 期间开通数（含新客与唤回） |
| 流失 | Float(precision=0) | 76 | `216` | 期间流失数 |
| 净增 | Float(precision=0) | 76 | `+178`（正绿负红） | 新增 − 流失 |
| 期末在服 | Float(precision=0) | 92 | `4,838` | 时点存量（北极星） |
| 流失率 | Percent(precision=2) | 84 | `4.87%` | 流失数 ÷ 分母（按口径开关） |
| 新增 MRR | Currency(precision=0) | 100 | `¥136,938` | 期间新增记录的 MRR 合计 |
| 流失 MRR | Currency(precision=0) | 100 | `¥33,410` | 期间流失记录的 MRR 合计 |
| 净 MRR | Currency(precision=0) | 100 | `¥103,528`（正绿负红） | 新增 MRR − 流失 MRR |
| 新增 ARPU | Currency(precision=0) | 96 | `¥347` | 新增 MRR ÷ 新增用户数 |
| 平均生命周期(天) | Float(precision=1) | 112 | `412.3` | 期间流失样本的生命周期均值 |
| 环比 | Percent(precision=1) | 78 | `+12.4%` | 净增与上一期间对比（首期显示 —） |
| 同比 | Percent(precision=1) | 78 | `+8.1%` | 净增与去年同期对比（不足 12 个月显示 —） |

设计说明（三条易踩的坑）：

1. **人数为什么用 Float(0) 而不是 Int**：Frappe 的 `Int` 格式化是 `cint` 直出，不加千分位；
   人数是四位数到五位数，`Float(precision=0)` 才能得到 `4,838` 这种可读格式，导出到 Excel 仍是数字。
2. **比率必须用 Percent**：框架会按 `precision` 自动补 `%` 并右对齐；把单位写在列名里（如"流失率(%)"）
   既啰嗦又容易漏。金额同理用 Currency，由站点货币（CNY）决定货币符号。
3. **「新客 / 唤回」不再占用主表列**：它是「新增」的拆分明细，放在主表里既占宽又打断阅读节奏；
   需要时在大屏 KPI（新增卡片的副文案）或单据列表按生命周期序号筛选查看。
4. **关掉表头下方的「行内筛选行」**：`frappe-datatable` 默认 `inlineFilters: true`，会在表头下
   渲染一排输入框（每个列头一个）。14 列的分析报表里这排输入框只是噪音，而报表顶部已有完整
   筛选栏，因此在报表 JS 的 `get_datatable_options()` 里显式关闭（框架会在构造 datatable 前调用该钩子）。

### 8.3.1 合计行规则（不由框架生成）

框架的合计行是**逐列盲求和**：它会把"流失率"逐月相加（得到 58% 这种假数字）、
把"期末在服"逐月相加（得到各月存量之和）。因此本报表：

- 返回值里输出 `skip_total_row = True`，并在 `Report.add_total_row` 置 0，关掉框架合计行；
- 自己追加一行「合计」（行内带 `is_total` 标记，前端会加粗），按指标口径重算：
  期初/期末取时点值、新增/流失/MRR 取区间累计、**流失率按区间整体重算**（不是逐月平均）、
  环比取净增与上一等长区间对比；
- 合计行的流失率是"区间整体口径"（例如 12 个月累计流失率），与各行的"单期流失率"含义不同，
  这一点由表格上方的口径说明与本文档共同兜底。

### 8.4 输出列定义（分组模式）

选择分组维度后，报表转为"期间 × 维度值"的透视结构，每个维度值下包含新增、流失、净增、在服四个子指标：

| 期间 | 维度值 A | 维度值 B | … |
| --- | --- | --- | --- |
| 2026-07 | 新增 / 流失 / 净增 / 在服 | 新增 / 流失 / 净增 / 在服 | … |

**设计取舍**：采用"每个维度值一组子列"而非多张表，好处是可在同一屏横向对比渠道或区域表现；当维度值超过 8 个时，提示并默认只保留前 8 名加"其他"，避免表格横向溢出。

### 8.5 计算逻辑与实现策略

```
1. 解析并校验筛选器（区间合法、粒度与区间匹配、维度值合法）
2. 生成时间桶列表（按粒度切分区间）
3. 一次性取出区间内的最小必要字段（开通日期、流失日期、MRR、分组维度）
   —— 条件全部下推到 SQL，使用参数化占位符
4. 期间计数与区间重叠计数两遍扫描，累计各桶指标
5. 计算比率类指标（流失率、ARPU、环比、同比），处理分母为 0
6. 组装列定义与数据行，附口径说明与筛选条件摘要
7. 写入缓存（键 = 筛选条件指纹），默认存活 60 秒
```

| 关注点 | 策略 |
| --- | --- |
| SQL 形态 | 期间计数按日期分组聚合；存量计数按时点条件统计后再做桶间累计 |
| 参数化 | 所有筛选值通过占位符传入，禁止字符串拼接 |
| 缓存 | 相同筛选条件的重复访问走缓存；数据写入时按前缀失效 |
| 空结果 | 返回列定义加空数据与明确空态提示，而非报错 |
| 大区间保护 | 区间超过 24 个月且粒度为日时提示并建议切换粒度 |
| 汇总行 | 绝对量求和；比率类按汇总后的分子除以分母重算 |

### 8.6 图表设计

| 图表 | 类型 | 数据来源 | 设计要点 |
| --- | --- | --- | --- |
| 增长与流失趋势 | 组合图：柱（新增、流失）+ 折线（期末在服） | 期间三个核心序列 | 双 Y 轴，左轴人数、右轴存量；图例可点击隐藏 |

图表随筛选条件联动；数据点超过 90 个时自动精简标签，避免文字重叠。图表容器必须设置固定高度，防止加载过程中的布局抖动。

## 9. 大屏页面设计：增长大屏

### 9.1 设计决策记录（ADR-002）：大屏的交付形态

| 维度 | 方案 A：Desk 标准页面（采纳） | 方案 B：应用内 Web 页面路由 |
| --- | --- | --- |
| 与需求匹配 | 直接对应需求中的"页面（Page）" | 属于 Web 页面，不是框架意义上的 Page |
| 天然能力 | 可挂角色权限、可放在工作区、路由固定 | 需自行处理登录态与访问控制 |
| 沉浸感 | 需隐藏 Desk 顶栏与侧边栏（CSS 类切换） | 天然全屏，无框架外壳 |
| 维护成本 | 低，无额外部署单元 | 中，多一套访问入口与权限配置 |
| 结论 | **作为主交付**，满足字面需求且具备权限体系 | 作为"极致沉浸"备选，仅在方案 A 无法达标时启用 |

**决策**：采用方案 A，并实现"沉浸模式切换"：

1. 常规模式：保留 Desk 顶栏与侧边栏，便于在大屏与分析页面之间切换（巡检、演示场景）。
2. 沉浸模式：一键隐藏顶栏与侧边栏，内容区占满视口，进入浏览器全屏；按退出键或再次点击还原。
3. 两种模式共用同一套渲染逻辑，仅切换外层布局类，避免维护两份代码。

### 9.2 页面结构与布局蓝图（基准 1920 × 1080）

**容器层次**

```
        └── 全局样式与主题令牌（含沉浸模式类）
```

**落地要点（Frappe v15 的实际加载机制，踩过坑）**

1. 页面的 HTML **不能**写在 Page 的 JSON 里：Page 文档表（`tabPage`）没有内容列，
   `content` 只是一个恒为 null 的伪字段。骨架必须放在同目录的 `.html` 模板文件里，
   由 `Page.load_assets()` 注册成 `frappe.templates["growth_dashboard"]`，页面 JS 用
   `frappe.render_template("growth_dashboard", {})` 取出并挂到 `page.main`。
2. 框架把该 `.html` 塞进一个**单引号 JS 字符串**，并且会先压缩空白、去掉 HTML 注释，
   所以模板里不能出现 ASCII 单引号（否则整页白屏、且只在浏览器里才看得出来）。
3. 页面脚本的写法是 `frappe.pages["<name>"].on_page_load = function (wrapper) {...}`：
   `frappe.pages[name]` 由 `frappe.container.add_page()` 在脚本 eval 之前创建为 wrapper 元素，
   因此脚本里直接赋值是安全的；这也是框架自带页面（如 `dashboard_view.js`）的写法。

### 9.7 多分辨率适配

采用"固定逻辑画布 + 整体等比缩放"方案：设计稿逻辑尺寸固定为 1920 × 1080，运行时按视口计算缩放比例并居中，从而保证任意分辨率下元素比例与相对位置完全一致。

| 分辨率 | 缩放策略 | 预期效果 |
| --- | --- | --- |
| 1366 × 768 | 按宽度等比缩小 | 内容完整，文字按比例变小但仍可读 |
| 1920 × 1080 | 1:1 | 设计稿效果 |
| 2560 × 1440 | 等比放大 | 保持视觉密度，不出现过大空白 |
| 3840 × 2160 | 等比放大（2 倍） | 远距离展示，线条与字号同比例增强 |
| 超宽屏（大于 21:9） | 主画布居中，两翼留白并填充环境信息 | 避免拉伸变形 |

**实现要点**

1. 缩放比例取"视口宽度 ÷ 1920"与"视口高度 ÷ 1080"中的较小值，保证不裁切。
2. 缩放使用整体变换而非逐个元素调整，避免局部错位。
3. 图表在缩放容器内渲染时使用"逻辑像素"尺寸，缩放后由浏览器统一处理，避免模糊与重绘抖动。
4. 窗口尺寸变化时防抖处理（约 200ms），避免拖拽调整窗口时反复重排。

### 9.8 可访问性与展示友好性

| 关注点 | 设计 |
| --- | --- |

| 动效可控 | 支持关闭数字滚动与轮播 |
| 图表可访问替代 | 每个面板提供"查看数据表"入口，以表格形式展示同一数据，供色觉障碍或需要精确取值的用户使用 |

## 10. 后端接口设计

### 10.1 统一响应结构

```
{
  "code": 0,
  "msg": "ok",
  "generated_at": "2026-10-09 14:32:05",
  "caliber": {
    "active_users": "区间重叠法（期末时点）",
    "churn_rate_denominator": "期初在服用户数",
    "timezone": "Asia/Shanghai"
  },
  "cached": true,
  "data": { }
}
```

设计要点：`generated_at` 供前端展示"最后更新时间"；`caliber` 让前端可把口径直接渲染到状态栏，做到"数字自证"；`cached` 用于运维排查与缓存命中率统计。

### 10.2 接口清单

| 接口 | 用途 | 主要参数 | 缓存 | 权限 |
| --- | --- | --- | --- | --- |
| `get_dashboard_data` | 首屏全量数据（KPI、趋势、地域、渠道、流失原因、重点客户） | 时间范围、粒度、区域、渠道、套餐 | 60 秒 | 报表读取权限 |
| `get_kpi_summary` | 仅 KPI（轻量刷新） | 时间范围、筛选条件 | 60 秒 | 同上 |
| `get_trend_series` | 趋势序列（粒度切换） | 时间范围、粒度、筛选条件 | 60 秒 | 同上 |
| `get_region_breakdown` | 地域分布与下钻 | 大区或省份 | 60 秒 | 同上 |
| `get_churn_reasons` | 流失原因分布 | 时间范围、筛选条件 | 120 秒 | 同上 |
| `get_top_accounts` | 重点客户榜单 | 时间范围、数量上限 | 120 秒 | 同上 |
| `get_event_feed` | 动态事件流 | 数量上限 | 不缓存 | 同上 |
| `get_filter_options` | 筛选器选项（含枚举字典） | 无 | 1 小时 | 登录用户 |

### 10.3 参数约定

| 参数 | 类型 | 默认 | 约束 |
| --- | --- | --- | --- |
| `range` | 文本或日期对 | 近 30 天 | 必须可解析，结束日期不早于开始日期 |
| `granularity` | 枚举 | 日 | 日 / 周 / 月；与区间长度匹配校验 |
| `region` | 枚举或多值 | 全部 | 必须来自枚举字典 |
| `channel` | 枚举或多值 | 全部 | 同上 |
| `plan` | 枚举或多值 | 全部 | 同上 |
| `limit` | 整数 | 10 | 1~50，防止单次返回过大 |

**校验原则**：参数非法一律返回参数错误而不是静默兜底（前端可据错误码回退到默认值），避免"用错口径却看不出错"。

### 10.4 缓存设计

| 项 | 设计 |
| --- | --- |
| 缓存介质 | 应用缓存（Redis） |
| 缓存键 | **数据集名（namespace）+ 载荷结构版本 + 筛选条件指纹 + 数据版本**，四段拼成，见下方说明 |
| 存活时间 | KPI 与趋势 60 秒；流失原因与榜单 120 秒；筛选选项 1 小时 |
| 失效时机 | 键里带上「数据版本」（`MAX(modified)`），任何写入都会自动切到新键，不依赖"记得清缓存" |
| 缓存穿透保护 | 空结果也缓存（较短存活时间），避免高频空查询压库 |
| 可关闭 | 提供开关，便于核对实时数据与排查缓存问题 |

**三个必须遵守的细节（都踩过坑）**

1. **每个接口必须有独立的 namespace**：曾经整包接口（`get_dashboard_data`）与趋势接口
   （`get_trend_series`）共用缓存键 —— 同一次筛选下，谁先请求谁把结果写进同一个键，
   后请求的接口就会读到别人的载荷。表现是：切回"日"粒度后趋势图空白（趋势接口拿到了
   没有 `labels` 字段的整包数据），而且只在缓存有效期内、顺序恰好时复现，属于典型
   "有时候没数据"。现在键里带上 `dashboard` / `kpi` / `trend` / `region` / `churn` / `top`
   等数据集名，物理隔离（`_cache_key()` 统一生成，回归用例见 `test_api.py`）。
2. **`frappe.cache().get_value()` 会写「请求级 memo」**：它在 `frappe.local.cache` 里缓存
   读到的值，**连未命中也会记成 None**（`expires=True` 只影响是否写入 memo，不绕过读取），
   因此"写完后立刻读"在同一进程里会失真。判断缓存是否真的生效，要看**跨请求**行为
   （HTTP 连调两次看 `cached` 字段）或用底层 client 直读 Redis。
3. **TTL 由 Redis `setex` 保证**：`set_value(..., expires_in_sec=N)` 走的就是 `setex`；
   上面的 memo 会让"同进程内测 TTL"看起来失效，实际跨请求是正常的。

### 10.5 错误码与异常表现

| 错误码 | 含义 | 触发场景 | 前端表现 |
| --- | --- | --- | --- |
| 0 | 成功 | — | 正常渲染 |
| 401 | 未登录 | 会话过期 | 提示重新登录 |
| 403 | 无权限 | 角色未授权 | 面板与整屏均显示无权限提示 |
| 412 | 参数非法 | 区间或枚举非法 | 提示并回退默认时间范围 |
| 429 | 请求过于频繁 | 高频轮询 | 延长刷新间隔并提示 |
| 500 | 服务端异常 | 计算或数据库异常 | 面板级错误加重试按钮，并记录日志 |
| 504 | 计算超时 | 区间过大或数据量激增 | 提示缩小时间范围 |

### 10.6 接口与大屏的调用时序

```
打开大屏
  → get_filter_options（取枚举与可选值，可缓存 1 小时）
  → get_dashboard_data（首屏全量，1 次请求）
  → get_event_feed（实时事件，独立请求，失败不影响主屏）
定时器（60 秒）
  → get_kpi_summary + get_trend_series（增量刷新）
用户切换时间范围或粒度
  → 取消进行中的旧请求 → 发起新请求 → 局部更新
```

**并发控制**：同一面板同一时刻只保留一个在途请求；新请求发起时废弃旧请求结果，避免"后到的旧数据覆盖新数据"。

## 11. 权限、安全与合规

### 11.1 权限模型

| 层级 | 机制 | 说明 |
| --- | --- | --- |
| 角色层 | 3 个角色：系统管理员、增长分析师、增长观察者 | 见 6.9 权限矩阵 |
| 文档层 | 单据权限：读取/新建/修改/删除/导入/导出/报表 | 观察者只读，分析师可写不可删 |
| 字段层 | 派生字段只读；敏感字段（手机号、邮箱）脱敏或限定可见级别 | 即使引入真实数据也可直接启用 |
| 数据行层 | P1：按大区配置用户权限，并注入查询条件 | 实现"华东负责人只看华东" |
| 页面层 | 大屏页面绑定可见角色 | 未授权用户访问页面直接拒绝，而非渲染空屏 |
| 接口层 | 每个白名单接口内做角色与文档读取权限校验 | 页面能看、接口也必须能校验，二者不可互相替代 |

> 设计原则：接口不信任前端。所有权限判断必须在服务端完成，前端隐藏按钮只是体验优化，不构成安全边界。

### 11.2 敏感字段脱敏规则

| 字段 | 脱敏规则 | 示例 | 应用范围 |
| --- | --- | --- | --- |
| 手机号 | 保留前 3 位与后 4 位 | `138****1234` | 界面、导出、接口返回 |
| 邮箱 | 保留首字符与域名 | `a***@example.com` | 界面、导出、接口返回 |
| 用户名称（企业客户） | 保留前 2 字 | 星辰* | 大屏与报表等公共展示场景 |
| 用户标识 | 编号化展示 | `U-8F3A21` | 公共展示场景 |
| 流失原因详述 | 明细仅分析师可见 | — | 大屏不展示自由文本 |

系统默认展示脱敏值；分析场景下（分析师角色）可通过字段级权限查看完整值，导出行为记入日志。

### 11.3 接口安全

| 控制项 | 措施 |
| --- | --- |
| 访问控制 | 白名单接口 + 登录态校验 + 角色与文档权限校验，三重校验缺一不可 |
| 注入防护 | 全部查询参数化；禁止字符串拼接；枚举值必须在字典内 |
| 越权防护 | 记录级权限与数据行权限在服务端统一处理，前端传入的筛选条件不得绕过权限 |
| 请求频率 | 对聚合接口做轻量限流（如每用户每分钟上限），超出返回 429 |
| 输出规模 | 榜单类接口限制返回条数；聚合接口不返回明细级个人数据 |
| 传输安全 | 生产环境强制 HTTPS；跨域仅在明确需要时开启且限制来源 |
| 日志安全 | 日志中不记录完整手机号、邮箱与自由文本 |

### 11.4 大屏免登录方案（可选，默认关闭）

大屏常部署在会议室设备上，可能需要免登录常驻展示。设计上提供受控方案：

1. 默认关闭匿名访问。
2. 如启用，仅开放聚合接口（KPI、趋势、分布），永不开放明细接口。
3. 使用专用只读账号或受限令牌，并限制来源地址段。
4. 数据保证为聚合级且已脱敏，不包含可识别到个人的信息。
5. 该能力需业务与安全共同确认后开启，并在交付说明中标注风险与限制。

### 11.5 审计与留痕

- 单据开启变更留痕，可追溯流失原因、健康分、状态等关键字段的修改历史。
- 导出与批量导入记录操作人与时间，便于数据外发追溯。
- 接口异常与权限拒绝写入日志，形成安全事件可追溯链。

### 11.6 合规要点

1. **数据最小化**：只收集业务分析必需的字段，不留存与用途无关的信息。
2. **合成数据优先**：演示与测试环境一律使用合成数据，避免真实个人信息扩散。
3. **用途限定**：字段与报表的设计用途聚焦经营分析，不做个体画像对外输出。
4. **告知与提示**：备注与附件字段在界面明确提示不要填写或上传个人敏感信息。

## 12. 错误处理、日志与可观测

### 12.1 分层错误处理策略

| 层级 | 典型错误 | 处理策略 | 用户感知 |
| --- | --- | --- | --- |
| 展示层 | 渲染异常、图表库加载失败 | 面板级捕获与降级，不影响其他面板 | 单面板显示错误占位 |
| 编排层 | 参数非法、区间过大 | 返回明确错误码与可操作建议 | 顶部提示并回退默认筛选 |
| 口径层 | 分母为 0、数据缺失 | 返回短横线或空集合，不抛异常 | 显示短横线或空态 |
| 数据层 | 查询超时、连接异常 | 捕获并记录日志，返回服务端错误 | 面板错误加重试按钮 |
| 数据准备层 | 重复数据、自检不通过 | 中断并输出违规明细 | 终端输出可读报告 |

### 12.2 日志规范

| 项 | 规范 |
| --- | --- |
| 日志前缀 | 统一前缀便于检索，如按模块标注 `[user_growth][screen]`、`[user_growth][report]`、`[user_growth][seed]` |
| 记录内容 | 接口名、关键参数（脱敏后）、耗时、缓存命中、异常堆栈 |
| 不记录 | 完整手机号、邮箱、自由文本型备注 |
| 分级 | 信息（成功但值得观察）、警告（可降级）、错误（需处理） |
| 位置 | 框架标准错误日志与站点日志，交付文档给出访问方式 |

### 12.3 可观测项

| 指标 | 用途 | 关注阈值 |
| --- | --- | --- |
| 大屏接口响应时间 | 判断是否触发性能预算 | P95 超过 800 毫秒需排查 |
| 报表查询时间 | 判断数据量与索引效果 | P95 超过 1.5 秒需排查 |
| 缓存命中率 | 判断缓存键与存活时间是否合理 | 低于 60% 需复核 |
| 接口错误率 | 发现异常突增 | 5 分钟内错误率超过 5% |
| 数据生成耗时 | 判断写入策略是否退化 | 超过 10 秒需优化 |

### 12.4 常见异常处置流程

1. 用户报告"大屏某个面板没数据" → 先看该面板接口返回（浏览器网络面板）→ 再看服务端日志 → 再直接查询数据库核对区间内是否存在数据。
2. 报表与大屏数字不一致 → 检查时间范围与筛选条件是否完全一致 → 检查是否命中不同口径开关 → 检查缓存是否需要失效。
3. 刷新后数据未变 → 检查缓存存活时间与失效逻辑 → 检查是否处于暂停刷新状态。

### 13.3 调试手段

| 场景 | 手段 |
| --- | --- |
| 验证指标口径 | 在控制台调用口径层函数，与手写查询结果比对 |
| 验证接口 | 登录后直接访问接口路径，观察返回结构与耗时 |

| 验证样式 | 使用浏览器设备模拟切换分辨率，再到大屏实机核对 |

### 13.4 常见问题排查

| 症状 | 可能原因 | 处理 |
| --- | --- | --- |
| 页面或大屏 404 | 应用未安装、静态资源未构建、页面未生效 | 安装应用、重建资源、重启服务 |
| 大屏白屏 | 前端脚本异常 | 查看浏览器控制台，定位报错行 |
| 面板无数据 | 未生成数据或区间无数据 | 执行数据生成、调整时间范围 |
| 数字与预期不符 | 口径或筛选条件不同 | 对照口径速查卡，统一筛选条件 |
| 权限被拒 | 角色未授权或数据行权限限制 | 检查角色与权限配置 |
| 图表不显示 | 图表库未加载或容器高度为 0 | 检查资源路径与容器样式 |
| 修改未生效 | 缓存未失效或监听进程未运行 | 清缓存、确认监听进程 |
| 样式错乱 | 分辨率不同或缩放容器未生效 | 检查缩放比例计算与容器尺寸 |

### 13.5 开发工作流建议

| 变更类型 | 工作流 |
| --- | --- |
| 改字段 | 改元数据 → 表单脚本同步显隐与校验 → 重生成或补数据 → 验证列表与报表 |
| 改口径 | 只改口径层 → 跑口径单测 → 核对报表与大屏一致性 |
| 改报表 | 改编排层与前端脚本 → 用固定数据集断言结果 → 核对导出 |
| 改大屏 | 改视图模块 → 4 档分辨率回归 → 挂屏 30 分钟观察 |

### 14.2 单据单元测试用例

| 用例 | 输入 | 期望 |
| --- | --- | --- |
| 未来开通日期 | 开通日期为明天 | 保存失败，提示不能是未来日期 |
| 流失早于开通 | 流失日期早于开通日期 | 保存失败 |

| 状态流转 | 填入流失日期 | 状态变为已流失 |

| 缺失项警告 | 未填健康分 | 保存成功但给出警告 |

### 14.3 指标计算测试（固定小数据集）

用一份可读的小数据集（例如 6 个用户、跨 3 个月、含 1 个唤回用户）作为基准，对每个指标断言精确值：

| 指标 | 断言方式 |
| --- | --- |
| 新增与流失 | 精确等于预设条数 |
| 期初、期末在服 | 精确等于人工计算结果 |
| 净增长 | 新增减流失，且与期末减期初的差额关系自洽 |
| 流失率 | 按两种分母口径分别断言 |
| 平均生命周期 | 与手工计算一致 |
| MRR 类指标 | 与逐条累加一致 |
| 唤回识别 | 序号大于 1 的记录同时计入新增与唤回列 |

> 自洽性断言（期末在服 − 期初在服 = 新增 − 流失）是最有效的一类测试，能一次性发现口径实现中的大部分错误。

### 14.4 报表测试

| 用例 | 期望 |

| 分组模式 | 各分组值之和等于不分组时的总量 |
| 汇总行 | 绝对量等于各行之和，比率为重算值而非简单平均 |

| 空数据区间 | 返回空数据与空态提示，不报错 |

## 15. 部署方案

### 15.1 三类环境

| 环境 | 目的 | 数据 | 特点 |
| --- | --- | --- | --- |
| 开发环境 | 迭代与调试 | 合成数据（可随时重建） | 开启开发者模式，热重载 |
| 演示环境 | 评审与展示 | 合成数据（固定随机种子） | 稳定优先，预先生成数据 |
| 生产环境（可选） | 实际使用（本期不承诺） | 真实数据 | 关闭开发者模式，进程托管与备份 |

### 15.2 演示环境准备流程

1. 按第 2.3 节完成环境与应用安装。
2. 生成 mock 数据（固定随机种子，保证每次演示数据一致）。
3. 创建演示账号并分配角色。
4. 准备大屏入口（桌面快捷方式或固定标签页）。
5. 执行演示脚本自检一次。

### 15.3 生产化要点（若需要）

| 项 | 要点 |
| --- | --- |
| 进程托管 | 使用框架提供的生产化流程（进程管理加反向代理）替代开发启动方式 |
| 静态资源 | 构建后由反向代理直接提供，避免动态进程压力 |
| 开发者模式 | 关闭，避免调试信息暴露 |
| 定时任务与后台任务 | 启用，支持缓存预热与定时预计算 |
| 备份 | 定期数据库备份，保留最近若干份 |
| 日志轮转 | 配置日志轮转，避免磁盘写满 |
| 安全 | 强制 HTTPS，限制管理账号来源，开启访问审计 |

### 15.4 应用安装、升级与卸载

| 操作 | 流程 | 注意 |
| --- | --- | --- |
| 安装 | 拉取代码 → 安装依赖 → 安装应用到站点 → 构建资源 → 生成数据 | 首次安装后建议立即生成数据 |
| 升级 | 拉取新版本 → 执行迁移补丁 → 重建资源 → 清理缓存 → 重启 | 结构变更必须提供可回滚的补丁 |
| 卸载 | 卸载应用 → 按需清理数据 | 明确数据是否保留，避免误删生产数据 |

### 15.5 数据初始化与重置

| 场景 | 操作 | 结果 |
| --- | --- | --- |
| 首次初始化 | 执行数据生成入口 | 生成 24 个月数据并输出摘要与自检报告 |
| 重复执行 | 再次执行 | 跳过已存在记录（幂等），输出跳过数量 |
| 重置演示数据 | 带重置参数执行 | 清理旧批次数据后重新生成 |
| 完全清空 | 删除全部服务记录 | 列表与报表回到空态，用于演示空数据体验 |

### 15.6 备份与恢复

- 每次演示前建议做一次带文件的备份，出现问题可快速回滚。
- 恢复前先确认目标站点，避免误覆盖；恢复后清理缓存并核对数据条数。

### 附录 F 实现说明（落地时与本文档的差异与取舍）

实现阶段对本文档做了三处有意调整，理由如下——调整后文档与代码保持一致（对应 NFR-06 可维护性要求）。

| 项 | 本文档原设计 | 实现采用 | 原因 |
| --- | --- | --- | --- |
| 可视化 | 单一图表库（离线打包） | 应用内自绘 SVG 图表（`charts.js` 约 400 行，零依赖） | 大屏只需柱线组合、横向条形、环形、迷你趋势四种图形；自绘可保证完全离线、无许可与版本风险，且配色/字号/间距严格贴合视觉令牌 |
| 模块名 | 用户增长分析（中文） | `Growth Analytics`（ASCII），中文体现为应用标题 | Frappe 模块目录同时是 Python 导入路径，且会被前端构建工具扫描；ASCII 目录名可避免路径与构建兼容问题 |
| 暂停状态 | 由 P1 子表或手工字段承载 | 主单据增加 `is_paused`（Check）字段 | 状态机需要「已暂停」态，且必须与「已流失」严格区分（暂停不计入流失口径），用显式字段最不容易出错 |

另外补充三点实现层的说明：

1. **报表图表双通道**：`execute()` 同时返回 chart（第 4 个返回值），报表页脚本也提供 `get_chart_data`，
   以兼容不同大版本对报表图表的处理差异；两者数据同源，不会出现两套口径。
2. **运行环境**：通过 Docker 承载（Windows 不支持 Frappe 原生运行）。
   应用源码以卷挂载进容器，站点数据放在命名卷，`docker/entrypoint.sh` 全过程幂等，
   可反复 `docker compose up` 而不会重复建站或重复灌数据。
3. **视觉验证工具**：`tools/preview/` 复用与正式页面完全相同的前端资源，
   只把接口调用替换为读取数据快照，配合容器内的 headless chromium 可自动出图，
   使"大屏好不好看"从主观判断变成可复核的证据（截图保留在仓库中）。

#### G.2 落地过程中发现并修掉的真实问题

这 10 个问题都是"跑起来才会暴露"的，也正是把文档落成代码的价值所在。

| # | 现象 | 根因 | 处理方式 |
| --- | --- | --- | --- |
| 1 | 挂载进来的应用 import 失败（`No module named 'user_growth'`） | `bench` 不会为挂载目录做 editable install，应用也没登记在 `sites/apps.txt` | entrypoint 依据 `apps/` 真实目录重建 `apps.txt`，并写入 `.pth` 把应用加入 `sys.path` |
| 2 | 批量灌数据报 `Column 'days_to_expiry' cannot be null` | Frappe 建表时数值列是 NOT NULL | 写入前按元数据把数值字段的 `None` 归零 |
| 3 | `bench execute user_growth.seed.runner.run_cli` 报 `NameError: user_growth` | 该命令用 `eval` 求值，全局命名空间里只有 `frappe` | 改用"带站点上下文的 Python 入口"（`tools/seed.sh`），文档同步更新 |
| 4 | 容器内初始化时报 `FileNotFoundError: /home/frappe/logs/database.log` | frappe 日志句柄用相对路径 `../logs`，工作目录必须是 `<bench>/sites` | 初始化脚本内 `os.chdir(<bench>/sites)` |
| 5 | 流失单据不填原因也能保存 | **Frappe 会把 Select 字段默认成"第一个选项"**，`churn_type` 被自动填成"主动流失" | 对"必须显式选择"的 Select（省份、行业、流失类型、流失原因）加前导空选项，配合必填校验 |
| 6 | 报表接口 500：`No module named '...report.用户增长与流失分析'` | 脚本报表的模块路径由**报表名**拼出 | 目录与文件名改为与报表名完全一致 |
| 7 | 大屏 bundle 404 | `bench build` 产物带内容 hash（`user_growth.bundle.<hash>.js`） | 在 `hooks.py` 用 `app_include_js` 声明逻辑名，框架通过 `assets.json` 解析成真实路径 |
| 8 | 接口 500：`Object of type date is not JSON serializable` | KPI 的 `period` 与缓存键把 `date` 对象带进了 `json.dumps` | 统一转字符串，并新增"接口载荷必须可序列化"的回归测试 |
| 9 | "年"粒度与"月"粒度的合计对不上 | 为算同比而扩展的时间区间，让"跨区间起点"的第一个桶统计了区间外的数据 | 只裁剪跨越起点的那一个桶；用单测锁定"合计与粒度无关" |
